Engineered as a robust full-stack web application utilizing Python and the Django framework, this specification details the functional capabilities, forensic integrity controls, external interfaces, non-functional quality attributes, and analysis models governing the system. 1.2 Scope

System Identification & Demarcation: This subsection formally demarcates the operational and legal scope of the software product:

(1) Product Name: Digital Companion for Drug Field Testing (Engineering Code: FieldTest Companion, Django Package: drug_field_companion).

(2) System Capabilities: The application captures, catalogs, and manages seized narcotics cases; generates unique sequential reference codes; documents presumptive colorimetric test kit results; enforces kit expiration rules; records an unbroken chronological chain-of-custody ledger; provides a secure private evidence file vault; and enforces a mandatory two-person supervisory review workflow before generating court-admissible forensic summary reports.

(3) Explicit Negative Scope: FieldTest Companion does not perform automated molecular identification, does not interpret raw spectrometry data, does not replace certified forensic toxicology laboratories, and does not provide operational recipes or instructions for chemical reagent synthesis.

⚖ MANDATORY FORENSIC DISCLAIMER ENFORCEMENT "Field-test outcomes are presumptive screening results only. They do not establish the definitive identity of a substance. Confirmatory laboratory analysis is required." This statutory notice is systematically rendered across all user interfaces, field-entry forms, and official printable case reports in accordance with international forensic standards.

Application & Benefits: The application of FieldTest Companion resolves critical vulnerabilities inherent in conventional law enforcement field testing. By replacing handwritten notebooks with structured digital records, the platform eliminates illegible test documentation, enforces tamper seal recording, guarantees chronological chain-of-custody visibility, and ensures that preliminary screening evidence cannot be filed in judicial proceedings without explicit supervisory concurrence.

2. General Description

This section describes the overarching operational context, general factors, domain characteristics, and environmental constraints that govern FieldTest Companion. It establishes the conceptual foundation necessary to interpret the granular technical requirements articulated in Section 3.

2.1 Product Perspective

FieldTest Companion is a standalone, self-contained web platform engineered specifically for field investigation units, law enforcement precincts, and forensic liaison offices. Within the broader criminal justice information ecosystem, FieldTest Companion occupies the critical operational window between crime scene substance seizure and formal intake by an accredited forensic toxicology laboratory.

Historically, this operational window relied entirely on handwritten field notebooks and physical evidence tags. FieldTest Companion digitizes this boundary layer by interfacing with field officers via modern web browsers on mobile devices, tablets, and laptops. While the system operates as an autonomous web application with its own relational database, it produces standardized data exports and court-ready forensic summary reports designed for seamless downstream ingest into state Laboratory Information Management Systems (LIMS).

2.2 Product Functions

The primary functions delivered by FieldTest Companion are modularized across 8 decoupled Django applications:

1. Core Portal (core): Centralized operational dashboard providing real-time metrics on active investigations, pending supervisory reviews, recent seizures, and quick-action navigation.

2. Identity Management (accounts): Authentication, group role management (Field Officer, Supervisor, Administrator, Read-only User), and secure profile administration.

3. Case & Dossier CRUD (cases): Comprehensive incident cataloging, sequential reference generation (CASE-YYYY-XXXX), multi-criteria filtering, and sample management.

4. Specimen Inventory (cases): Physical specimen registration (SMP-YYYY-XXXX), tamper seal verification, packaging documentation, and initial condition assessment.

5. Field Testing Engine (testing_records): Presumptive reagent kit catalog, lot number and expiration tracking, sensory color observation recording, and controlled result categorization.

6. Chain of Custody (custody): Append-only chronological custody ledger tracking physical possession transfers, storage lockers, and automated out-of-sequence retrospective flags.

7. Secure Evidence Vault (evidence): Private evidence repository supporting photo and PDF attachments with MIME-type and size validation, accessible exclusively via authenticated streaming endpoints.

8. Supervisory Governance (reviews): Two-person supervisory review queue, mandatory actionable feedback validation, approval/revision state machines, and permanent case record locking.

9. Security Audit Log (auditlog): Silent chronological tracking of user authentication, case modifications, authorization denials, and system administrative actions with client IP capture.

2.4 General Constraints

The design and implementation of FieldTest Companion are governed by several foundational constraints:

Statutory Forensic Constraints: In strict adherence to safety standards and legal mandates, the application prohibits chemical formulation recipes, reagent manufacturing guidelines, and automated positive/negative chemical determinations. All field test outcomes must be labeled presumptive screening results.

Two-Person Integrity Rule: Under the Two-Person Integrity Principle, the user who creates a case or records a test event is strictly prohibited from approving that case. Supervisory approval requires an independent authenticated user belonging to the Supervisor role group.

Architectural Framework Constraints: The software is engineered exclusively in Python 3.12 utilizing the Django 5.x framework, relying on Django's built-in Model-Template-View architectural patterns without external third-party proprietary frameworks.

Evidentiary Storage Restrictions: All evidence files must be saved outside the web root in private media directories and served solely through streaming views requiring active user session validation.

Client Browser Compatibility: The interface must conform to responsive web standards (HTML5/CSS3/Bootstrap 5) and operate seamlessly across modern browsers (Google Chrome, Apple Safari, Mozilla Firefox, Microsoft Edge) without client-side native plugin dependencies.

2.5 Assumptions and Dependencies

The operational validity and runtime performance of FieldTest Companion assume the following technical dependencies:

Python Runtime: The server environment maintains an active Python 3.10+ execution environment with the Django framework and required dependencies installed as defined in requirements.txt.

Relational Persistence: The application utilizes SQLite 3 for local development and automated testing, and supports PostgreSQL 14+ for enterprise production deployment via Django ORM configuration.

Filesystem Storage Permissions: The host operating system must grant read and write filesystem permissions to the dedicated media/evidence directory for secure evidence document storage.

Time Synchronization: System clocks on the application host must be synchronized via Network Time Protocol (NTP) to guarantee chronological timestamp integrity for chain of custody and audit records.

Network Infrastructure: Field devices require TCP/IP network connectivity via mobile data (4G/5G) or Wi-Fi to synchronize field records with the central Django server.

3.2 Functional Requirements

The following 16 subsections document the individual functional requirements implemented within FieldTest Companion. Each requirement is uniquely numbered and structured according to the official format.

3.2.1 User Authentication and Session Management

3.2.1.1 Introduction: The system must authenticate registered personnel before granting access to forensic data, verifying credentials against salted PBKDF2 password hashes.

3.2.1.2 Inputs: Username (CharField), Password (CharField), CSRF Token (hidden input).

3.2.1.3 Processing: The authentication view verifies active user status, validates password credentials, establishes a secure HTTP-only session cookie upon success, logs authentication events in the audit trail, and redirects to the operational dashboard. POST-only logout destroys session data.

3.2.1.4 Outputs: Authenticated user session, personalized dashboard redirect, HTTP status 200/302, flash message.

3.2.1.5 Error Handling: Invalid credentials return 'Invalid username or password'; inactive accounts receive 'Account disabled'; unauthenticated requests redirect to login with 'next' parameter preservation.

3.2.2 Role-Based Access Control and Authorization

3.2.2.1 Introduction: The system must enforce strict role-based access control (RBAC) across four operational personas: Field Officer, Supervisor, Administrator, and Read-only User.

3.2.2.2 Inputs: User identity and associated group memberships stored in auth_user_groups.

3.2.2.3 Processing: Django view decorators (e.g., @role_required, @supervisor_required, @admin_required) inspect user group associations during view dispatch. If the authenticated user does not belong to an authorized group, access is immediately blocked.

3.2.2.4 Outputs: Authorized view rendering; or HTTP 403 Forbidden response with custom permission denied error page.

3.2.2.5 Error Handling: Unauthorized access attempts throw PermissionDenied exceptions, render friendly 403 error alerts, and trigger high-priority security audit log entries capturing user ID, IP, and requested URL.

3.2.3 Case Record Registration and Management

3.2.3.1 Introduction: The system must enable authorized officers to initialize, document, and manage criminal investigation case files recording incident background and circumstances.

3.2.3.2 Inputs: Incident Datetime (DateTimeField), Title (CharField), General Location (CharField), Operational Description (TextField), Assigned Officer (ForeignKey User).

3.2.3.3 Processing: CaseRecordForm validates that incident datetime is not in the future, verifies required text fields are populated, associates the creating officer, sets initial status to 'Draft', and saves the record in cases_caserecord.

3.2.3.4 Outputs: New CaseRecord entity created; user redirected to Case Detail view with confirmation notification.

3.2.3.5 Error Handling: Missing required fields trigger inline field errors ('This field is required'); future incident dates raise ValidationError; unauthenticated submissions redirect to login.

3.2.4 Automated Case Reference Identifier Generation

3.2.4.1 Introduction: The system must automatically generate a standardized, unique, sequential case reference code to ensure unambiguous evidentiary tracking.

3.2.4.2 Inputs: Current calendar year (YYYY), sequential integer query against existing cases in the active database.

3.2.4.3 Processing: Upon saving a new CaseRecord with an unassigned reference, the model queries the maximum existing sequential identifier for the current calendar year, increments the sequence by 1, and formats the string as CASE-YYYY-XXXX (e.g., CASE-2025-0001).

3.2.4.4 Outputs: Populated case_reference field stored in the database and displayed prominently across all dossier views.

3.2.4.5 Error Handling: Database race conditions during concurrent case generation are mitigated through atomic transaction blocks and unique database constraints on case_reference.

3.2.5 Physical Seizure Sample Cataloging and Validation

3.2.5.1 Introduction: The system must enable officers to catalog individual physical substance specimens seized during an investigation, linking each sample to its parent CaseRecord.

3.2.5.2 Inputs: Sample Code (optional CharField), Collected Datetime (DateTimeField), Physical Description (TextField), Packaging Reference (CharField), Seal Reference (CharField), Initial Condition (CharField).

3.2.5.3 Processing: SampleForm validates that Collected Datetime is not prior to the parent case Incident Datetime; generates an auto-assigned SMP-YYYY-XXXX identifier if left blank; enforces strict sample_code uniqueness; and associates the sample with the parent CaseRecord.

3.2.5.4 Outputs: Persisted Sample record in cases_sample; sample inventory updated on Case Detail view.

3.2.5.5 Error Handling: Duplicate sample codes trigger 'Sample code is already registered'; collection dates preceding incident datetime raise ValidationError; missing packaging references trigger validation warnings.

3.2.6 Colorimetric Test Kit Catalog Management

3.2.6.1 Introduction: The system must maintain an administrative catalog of authorized presumptive colorimetric test kits, tracking commercial metadata and safety notices.

3.2.6.2 Inputs: Kit Name (CharField), Manufacturer (CharField), Category (CharField), Catalogue Reference (CharField), Active Status (BooleanField), General Safety Note (TextField).

3.2.6.3 Processing: TestKitForm validates catalog references, enforces that general safety notes do not contain hazardous chemical recipes, sets active status flags, and saves the entity in testing_records_testkit.

3.2.6.4 Outputs: Persisted TestKit catalog entry; kit becomes available in field test selection dropdowns.

3.2.6.5 Error Handling: Duplicate catalog references trigger validation rejection; non-admin users attempting catalog modifications receive HTTP 403 Forbidden.

3.2.7 Test Kit Expiration Validation and Justification Workflow

3.2.7.1 Introduction: The system must enforce strict expiration date safeguards preventing the unmonitored use of expired chemical reagent ampoules.

3.2.7.2 Inputs: Selected TestKit FK, Kit Expiry Date (DateField), Test Execution Performed Datetime (DateTimeField), Limitations Note (TextField).

3.2.7.3 Processing: During TestEventForm.clean(), the system compares test execution date against kit expiration date. If the execution date exceeds expiration date, the system strictly enforces that limitations_note must contain an explicit technical justification.

3.2.7.4 Outputs: Field test event recorded with flagged expiration justification; or form validation block.

3.2.7.5 Error Handling: If an expired kit is submitted without limitations notes, the form returns: 'The test kit is expired. You must provide an explicit justification in limitations notes.'

3.2.8 Presumptive Field-Test Event Documentation

3.2.8.1 Introduction: The system must document the execution and qualitative outcome of presumptive reagent screening tests performed on physical samples.

3.2.8.2 Inputs: Sample FK, TestKit FK, Kit Lot Number (CharField), Expiry Date (DateField), Performed Datetime (DateTimeField), Sensory Observation Notes (TextField), Result Category (ChoiceField).

3.2.8.3 Processing: TestEventForm validates that Result Category belongs to authorized choices (Not performed, Inconclusive, Presumptive positive, Presumptive negative, Invalid / Kit issue); logs sensory color reactions; persists record in testing_records_testevent.

3.2.8.4 Outputs: Persisted TestEvent record; outcome badge and sensory notes rendered in Case Detail test timeline.

3.2.8.5 Error Handling: Invalid result category choices rejected on server side; future execution timestamps blocked; kit lot numbers required.

3.2.9 Chronological Append-Only Chain of Custody Ledger

3.2.9.1 Introduction: The system must maintain an immutable, chronological chain-of-custody ledger tracking every transfer of physical evidence custody, storage check, or lab submission.

3.2.9.2 Inputs: Sample FK, Event Type (ChoiceField), Event Timestamp (DateTimeField), From Person (CharField), To Person (CharField), Location Reference (CharField), Seal Reference (CharField), Remarks (TextField).

3.2.9.3 Processing: CustodyEventForm validates transfer parties and location; detects whether the event timestamp is earlier than the latest existing custody event for the sample; automatically sets is_out_of_sequence=True for retrospective entries without rewriting historical records.

3.2.9.4 Outputs: New CustodyEvent appended to custody_custodyevent; rendered in chronological order with visual out-of-sequence warning badges where applicable.

3.2.9.5 Error Handling: Missing transfer parties trigger required field validation; unauthorized modifications to historical entries blocked by view permissions.

3.2.10 Private Evidence File Vault and Restricted Download Access

3.2.10.1 Introduction: The system must accept, validate, and securely store photographic and documentary evidence attachments outside public web roots, enforcing authenticated access.

3.2.10.2 Inputs: Case FK, Sample FK (optional), File Attachment (FileField), Caption (CharField), MIME type and file size.

3.2.10.3 Processing: EvidenceUploadForm validates file extensions (.jpg, .jpeg, .png, .pdf), validates MIME type, enforces a 10MB maximum file size limit, generates safe unique filenames, and saves files in private storage. Downloads are streamed exclusively via authenticated view.

3.2.10.4 Outputs: EvidenceFile saved in evidence_evidencefile; thumbnail/link displayed in Evidence vault tab.

3.2.10.5 Error Handling: Files exceeding 10MB rejected with 'File size must not exceed 10 MB'; disallowed extensions (.exe, .sh, .html) rejected with 'Unsupported file extension'; unauthenticated file downloads return HTTP 403/302.

3.2.11 Supervisory Review Queue and Decision Workflow

3.2.11.1 Introduction: The system must route submitted dossiers into an authorized supervisor review queue and enforce a formal two-person approval process before cases can be closed.

3.2.11.2 Inputs: Case FK, Reviewer User FK, Decision Choice ('Approved' or 'Changes requested'), Mandatory Comment (TextField).

3.2.11.3 Processing: ReviewForm enforces that comment cannot be blank and must be at least 5 characters; verifies user has Supervisor role; creates ReviewRecord; transitions CaseRecord.status to 'Approved' or 'Changes requested'; locks approved cases; fires audit signals.

3.2.11.4 Outputs: Persisted ReviewRecord; case status updated; dual-signature endorsement block activated on case report.

3.2.11.5 Error Handling: Blank or short comments trigger 'A supervisory review comment is strictly mandatory'; field officers attempting to submit reviews receive HTTP 403 Forbidden.

3.2.12 Revision Request and Re-submission Workflow

3.2.12.1 Introduction: The system must provide an iterative corrections workflow when a supervisor rejects or requests revisions to an investigation dossier.

3.2.12.2 Inputs: Supervisor review remarks, modified case metadata, corrected sample or test details.

3.2.12.3 Processing: Upon a 'Changes requested' decision, the case status shifts, unlocking the case for the assigned field officer. The officer addresses the supervisor's feedback, updates records, and re-submits the dossier back into the supervisory review queue.

3.2.12.4 Outputs: Case status updated to 'Submitted'; revision history tracked; notification badge displayed on supervisor dashboard.

3.2.12.5 Error Handling: Officers cannot re-submit without addressing required fields; supervisor remarks remain permanently visible in endorsement history.

3.2.13 Case Record Lockdown and Immutability Safeguards

3.2.13.1 Introduction: The system must permanently lock case records upon supervisory approval, preventing post-endorsement tampering or unauthorized evidentiary modification.

3.2.13.2 Inputs: CaseRecord.status == 'Approved' or 'Archived'.

3.2.13.3 Processing: Model-level save() methods and form dispatch views inspect case status. If the case is approved or archived, modification attempts to CaseRecord, Sample, TestEvent, or CustodyEvent are blocked unless an authorized supervisor performs an audited unlock command.

3.2.13.4 Outputs: Read-only rendering of forms; edit buttons replaced with locked status badges.

3.2.13.5 Error Handling: Direct POST requests attempting to alter locked records return HTTP 403 Forbidden and record security alerts in the audit log.

3.2.14 Case Search, Multi-Criteria Filtering, and Pagination

3.2.14.1 Introduction: The system must enable personnel to rapidly search and filter case records across multiple operational criteria with deterministic pagination.

3.2.14.2 Inputs: Search Keyword (CharField: reference, title, location, description), Status Filter (ChoiceField), Date Range (incident_from, incident_to), Page Number (int).

3.2.14.3 Processing: CaseListView constructs parameterized Django ORM querysets combining Q objects for keyword text search, exact status filtering, and incident date range filters; paginates results at 10 cases per page with query string preservation.

3.2.14.4 Outputs: Filtered case table with active filter badges, result counts, and pagination controls (Previous, Page X of Y, Next).

3.2.14.5 Error Handling: Malformed page parameters gracefully default to Page 1; invalid date strings ignored; queries with zero matches render an informative 'No matching cases found' empty state.

3.2.15 Court-Ready Forensic Case Report Generation

3.2.15.1 Introduction: The system must compile all verified case data into a clean, court-admissible forensic summary report with standardized print styling and PDF export capabilities.

3.2.15.2 Inputs: CaseRecord Primary Key (pk), authenticated user session.

3.2.15.3 Processing: The case_report_view retrieves the case, all child samples, chronological test events, custody transfers, evidence files, and supervisory review records; injects statutory legal disclaimers; and renders report.html styled for physical printing (@media print) and PDF download.

3.2.15.4 Outputs: Standardized, court-ready printable report view with browser print dialog trigger and dual-signature endorsement blocks.

3.2.15.5 Error Handling: Unapproved cases display a prominent 'PRELIMINARY / DRAFT REPORT' watermark; non-existent case IDs return HTTP 404 Not Found; unauthorized users receive HTTP 403.

3.2.16 Centralized Security Audit Logging and Event Tracking

3.2.16.1 Introduction: The system must maintain an automated, immutable audit trail tracking security-sensitive system activities, user authentications, and data modifications.

3.2.16.2 Inputs: Actor (User FK), Action (CharField), Object Type (CharField), Object ID (CharField), Summary (TextField), IP Address (GenericIPAddressField), Timestamp.

3.2.16.3 Processing: Django signal dispatchers (post_save, post_delete) and custom security middleware automatically instantiate AuditEvent records capturing request client IP addresses and operational event summaries without modifying core business tables.

3.2.16.5 Error Handling: Audit records are append-only; update() and delete() methods are prohibited in the administrative portal to maintain evidentiary admissibility.

Operational Uptime: Mean Time Between Failures (MTBF) exceeds 720 hours (30 continuous operational days) in standardized WSGI runtime deployments.

3.5.3 Availability

The platform is engineered for continuous precinct operations:

Stateless Web Workers: The application architecture is completely stateless across web workers, allowing horizontal scaling behind standard load balancers (e.g., Nginx).

Maintenance Downtime: Scheduled maintenance windows require less than 15 minutes per month, supported by automated zero-downtime database schema migrations.

Fault Recovery: Uncaught server exceptions trigger standardized 500 error pages while preserving existing session states and database integrity.

3.5.4 Security

Security is implemented in depth to safeguard sensitive criminal evidence and forensic chain of custody:

Cryptographic Password Hashing: Passwords are salted and hashed using PBKDF2 with a SHA-256 digest algorithm, conforming to NIST Special Publication 800-63B standards.

CSRF Defense: All state-changing HTTP POST requests mandate valid, cryptographically signed Cross-Site Request Forgery (CSRF) tokens.

SQL Injection Prevention: Django ORM parameterized query construction completely neutralizes Structured Query Language (SQL) injection attacks across all input fields.

XSS Protection: Django Template Language auto-escaping neutralizes Cross-Site Scripting (XSS) vectors across all dynamic user input strings.

Media Vault Isolation: Evidence media files are stored outside public web roots and accessed exclusively via authenticated streaming views with strict role checks.

3.5.5 Maintainability

Code maintainability is ensured through architectural modularity and rigorous documentation:

Decoupled Architecture: The codebase is cleanly partitioned into 8 decoupled Django applications following the Single Responsibility Principle.

Code Standards: Source code strictly complies with PEP 8 Python style guidelines, utilizing descriptive variable names, type hints, and comprehensive docstrings.

Test Coverage: Comprehensive test suite provides 100% test coverage across all critical acceptance test paths (AT-01 through AT-15).

3.5.6 Portability

FieldTest Companion is highly portable across diverse server environments:

Operating System Agnostic: Operates identically across macOS, Linux (Debian, Ubuntu, RHEL), and Microsoft Windows operating systems supporting Python 3.10+.

RDBMS Portability: Database portability allows seamless switching between SQLite 3 for localized testing and PostgreSQL 14+ for enterprise clustering via settings.py configuration.

Container Readiness: Container-ready architecture supports standard Docker containerization and WSGI application servers (Gunicorn, uWSGI).

3.7 Design Constraints

The architectural and implementation choices for FieldTest Companion were governed by specific external standards, institutional policies, and framework constraints:

Academic Syllabus Compliance: Implementation is strictly bound to the official syllabus and technology stack of INT253 (Python 3.12, Django 5.x, SQLite, Bootstrap 5). Third-party proprietary enterprise frameworks were prohibited.

Chemical Safety & Ethics: In accordance with legal ethics and safety standards, the platform strictly records qualitative color observations and kit lot numbers, but contains no chemical recipes, reagent formulas, or instructional guides for synthesizing controlled substances.
